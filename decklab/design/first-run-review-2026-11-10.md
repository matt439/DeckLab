# First-run review: installing and using Deck Lab as a newcomer (2026-11-10)

Seven reviewers each took one angle on a newcomer's first install and first use (installing on Windows, Linux and macOS, PostgreSQL and config.json, the page with an empty database, the docs, failure messages, upkeep). Commands were tried only in fresh clones with no config.json, never against the live database. A second agent checked each finding against the files; none was refuted, and some severities were lowered. The 76 findings are listed in full at the end; the stories E11-S78 to E11-S84 in [stories.md](stories.md) own the work, and each names the findings it covers by their number here.

## Verdict

On Windows, someone who is fairly comfortable with tools can get Deck Lab running. Someone who is new to this will stall at least once. The steps hold up: on a fresh clone, the venv, the pip install, the card data and the test server all worked as written, and `python -m decklab.doctor` is a good checklist. Most of the trouble is around those steps. The guide doesn't tell people which terminal to open or warn them about Python's PATH setting. It doesn't explain how to get PostgreSQL working or how to recover a forgotten `postgres` password. When something fails, the messages are often vague or wrong for a new install. My guess, not timed end to end, is about an hour on Windows if nothing goes wrong, and an afternoon if PostgreSQL does. **The biggest single obstacle is PostgreSQL.** Installing it, remembering its superuser password, keeping its service running and getting `db setup` through is where a newcomer is most likely to get stuck. The tools then describe all of those failures in the same words. Linux is well supported. macOS is noticeably thinner than the docs suggest. No review found a true blocker, but several issues will stop a newcomer until they find outside help.

## The first-run path as a newcomer experiences it

1. **Read README.md, then SELF-HOSTING.md** (ok). README is short and clear, but it says Deck Lab "runs on one Windows PC" and that Linux needs "your own service manager". Before step 1, SELF-HOSTING opens with a platform table, a WSL and CI status paragraph, a story id, and network ranges written in CIDR notation. There is no contents list, no time estimate and no hardware requirement.
2. **Install Git, Python 3.14 and PostgreSQL** (hard). There are no download links, no copy-paste install commands, and nothing about Python's "Add python.exe to PATH" checkbox or the Microsoft Store alias. The PostgreSQL installer's options aren't explained. The guide says to remember the postgres password "for step 4", but it's actually needed in step 5.
3. **Clone, then make the .venv and install psycopg** (ok). This works first time in PowerShell, but the guide never says to use PowerShell. In Git Bash, the `.venv\Scripts\python` command fails. The guide never explains what a .venv is.
4. **Create config.json** (ok, with traps). `cp` works in PowerShell. The guide's note for cmd (`copy` with forward slashes) fails. The step says "change the profile to yours" but shows the example's alex/Alex unchanged. It mixes in Linux-only notes and a mention of migration 0022 before any database exists. A byte-order mark, a trailing comma or a `"role": "Admin"` typo each fails silently or with a confusing error.
5. **Set up the database (`python -m decklab.db setup`)** (hard). It's one command when it works. If PostgreSQL is stopped, the user waits 10 seconds and gets "connection timeout expired", while the troubleshooting list only mentions "connection refused". If the installer password is forgotten, Windows has no recovery path. The guide gives no way to check that the PostgreSQL service is running.
6. **Card data (`python -m decklab.lib.cards update`)** (easy). It took about 20 seconds, with clear progress.
7. **Doctor and first start** (ok). This is the first time the guide mentions the doctor, even though it would have helped from step 2. The doctor's text is dense jargon. Its database line is identical for every cause, and it flags Java as UNVERIFIED for someone who skipped the optional simulations. The server starts cleanly even with nothing set up.
8. **First visit in the browser** (ok if setup succeeded, hard if not). Without a config, "Who are you?" says "No one has been added to Deck Lab yet." and gives no hint. Without the database, every page says "Try again in a minute", which never helps. When setup did succeed, the empty library offers Add a precon, Import cards and New deck, which works well. After that the user meets "wife" under Played by, words like Idea/Building/Built and Planned vs Play-now that the page never explains, and the "Who are you?" screen again on every visit.
9. **Run it in the background** (ok on Windows and Linux, hard on macOS). The documented Windows command leaves out `--at-logon`, so Deck Lab is off after every reboot and has no watchdog. macOS gets one line about launchd and one about cron, with nothing to copy.

## Top issues, ranked

None of these is a strict blocker. All are major, roughly in order of how many newcomers will hit them.

1. **The database failure messages describe every cause the same way.**
   - **Where:** `decklab/lib/preflight.py:53-54`, `preflight_local.py:368,390`, `decklab/db/conn.py:124-127`, `SELF-HOSTING.md:487`, the server console, and `web/version.js:75-85`.
   - **What happens:** The doctor prints the same line whether PostgreSQL is missing, stopped, on the wrong port, or has never been set up: "the cause is not classified as server downtime". A stopped Windows service gives "connection timeout expired", but the troubleshooting entry is keyed on "connection refused". The console says only "Database: not reachable." The page tells everyone "Try again in a minute", and on a fresh install it says pages show data "as they were when it was last reached". The real cause is written only to `decklab/data/logs/db.log`, and the guide never names that file.
   - **Fix:**
     - Separate "nothing answered at host:port" (is the `postgresql-x64-NN` service running?) from "connected but couldn't log in" (run `db setup`).
     - Point the doctor's Next line at `python -m decklab.db status`.
     - Add "connection timeout expired" to the troubleshooting entry, and say how to check the service (`Get-Service postgresql*`).
     - Print the reason on the console and name `db.log`.
     - Word the page messages by cause, and drop "last reached" when nothing was ever read.

2. **config.json errors crash the server or say nothing useful.**
   - **Where:** `decklab/lib/config.py:127,159`, `server.py:606`, `db/__main__.py:352-354`, `preflight.py:33`.
   - **What happens:**
     - A trailing comma makes the server print a full traceback.
     - The `db` commands print the bare parser message without naming the file.
     - A UTF-8 byte-order mark (written by PowerShell 5.1's `Set-Content`/`Out-File -Encoding utf8`) gives "Unexpected UTF-8 BOM".
     - The doctor says only "not valid".
     - Windows paths with single backslashes give "Invalid \escape", and the guide never says to double them.
   - **Fix:**
     - Read the file with `utf-8-sig`.
     - Catch `JSONDecodeError` and print "decklab/config.json isn't valid JSON: line L, column C", in the doctor too.
     - Add one sentence to step 4 about backslashes, and add a troubleshooting entry.

3. **A missing config leaves the page at a dead end.**
   - **Where:** `decklab/web/app.js:243` (and `settings.js:312`), and server startup.
   - **What happens:** With no config.json, or one saved as `config.json.txt`, the console prints nothing about it. The chooser says "No one has been added to Deck Lab yet." with no buttons and no hint, and the page has no way to add people.
   - **Fix:** At startup, log "No decklab/config.json: copy decklab/config.example.json (SELF-HOSTING.md step 4)". Change the empty box to say where profiles come from. Let `/api/status` report whether the config is missing or unreadable.

4. **A forgotten postgres password has no recovery path on Windows.**
   - **Where:** `decklab/db/setup.py:254-262`, `SELF-HOSTING.md:28,119-123,484-494`.
   - **What happens:** On Windows the hint is only "give the password set at install". POSIX users get a reset recipe. The guide has no "password authentication failed" entry.
   - **Fix:** Add that entry with the Windows recipe: set the 127.0.0.1 line in pg_hba.conf to trust, restart the service, run `psql -U postgres -h localhost -c "\password postgres"`, then switch the line back. Point setup's Windows hint at it.

5. **Restart is refused on an unzipped release once config.json exists.**
   - **Where:** `decklab/lib/build.py:71-72,189-196`, `scripts/make_release.py:60-72`, `lib/api/server_restart.py:99-101`.
   - **What happens:** config.json is part of the runtime fingerprint but not of the release manifest. The release therefore reads as changed: the footer warns about it and Settings refuses to restart. This was reproduced.
   - **Fix:** Leave config.json out of the comparison, and add a test that unzips a release, writes a config and expects it not to count as changed. It can't affect anyone yet, because no release has been published (see the minor list).

6. **On macOS, the smoke test reports a false PASS for the nightly backup.**
   - **Where:** `decklab/db/schedule.py:331-333`, `db/__main__.py:219-223`, `smoke.py:534-567`.
   - **What happens:** On darwin, `schedule status` prints "unsupported" but exits 0. The smoke test then reports "The nightly backup task is installed and its last run worked" when no backup has ever run.
   - **Fix:** Return an unsupported marker or a non-zero code, and have the smoke test report WARN: "no scheduler: add a cron/launchd job for `python -m decklab.db nightly`". Ideally also check `ops.backup_run`.

7. **macOS has no working stop, restart or update.**
   - **Where:** `decklab/lib/control.py:653-656`, `homenet/commands.py:367-371,609-611`, `update.py:480,516`, `SELF-HOSTING.md:289,324-338`, `README.md:26`, `scripts/decklab:2,34`.
   - **What happens:** `homenet stop`, `start` and `restart` all fail on darwin, so `python -m decklab.update` fails at its stop or restart step. `scripts/decklab` is documented for macOS but fails there with a Task Scheduler message about "starting at logon".
   - **Fix:** Add a darwin branch (SIGTERM for stop, `launchctl kickstart -k` for restart), or make update skip those steps with a note and document a manual update. Make `scripts/decklab` run the server in the foreground on darwin, and correct README:26.

8. **Homebrew PostgreSQL on macOS has no `postgres` role, and setup's hints are Linux-only.**
   - **Where:** `decklab/db/conn.py:24` (hard-coded `SUPERUSER`), `setup.py:239-262`, `SELF-HOSTING.md:28,115-123`.
   - **What happens:** Setup fails, and its hints say `sudo -u postgres psql` and `sudo systemctl reload postgresql`. Neither works on macOS.
   - **Fix:** Add a macOS paragraph: Postgres.app works as is; with Homebrew, run `brew services start postgresql@18 && createuser -s postgres`, then set a password. Optionally make the superuser configurable, and give darwin-specific hints.

9. **macOS background running and backups have nothing to copy.**
   - **Where:** `SELF-HOSTING.md:13,16,275,286`.
   - **What happens:** There is one line about launchd and one about cron. There is no example plist, and nothing explains launchd's minimal PATH (which hides Homebrew's tesseract, pg_dump and cloudflared), which Python to use, or that cron skips a night when the Mac sleeps.
   - **Fix:** Ship a LaunchAgent plist for the server and a calendar job or crontab line for `nightly`, or have `schedule preview-launchd` print them.

10. **Step 10, outside access, never explains how to create the Cloudflare setup.**
    - **Where:** `SELF-HOSTING.md:342-346`, `decklab/README.md:1227-1246`.
    - **What happens:** The reference describes one household's existing tunnel. The tunnel commands appear only under "Moving to another PC". config.yml is never shown as a file. Creating the Access application and finding its AUD tag are never explained.
    - **Fix:** Write a numbered how-to: add the domain; `cloudflared tunnel login`, `tunnel create` and `tunnel route dns`; an example config.yml with ingress to `http://127.0.0.1:8644` and `originRequest.access`; the Access application and where its team name and AUD tag are; the config.json blocks; then check with `homenet status`.

## What already works well

- **The doctor.** It runs with nothing installed, lists READY, NEEDS SETUP and NOT RUN in order with a "Next:" step for each, and writes nothing.
- **The setup steps on Windows.** The venv, the pip install, `cards update` (about 20 seconds) and the test server all worked first time in PowerShell. Every command the guide names exists and matches its `--help`.
- **The server without setup.** It starts with no config, no psycopg and no card data, and downloads the card data itself. Pages that need the database answer 503 with a reason instead of crashing.
- **`db setup`.** It is one command and safe to re-run. It creates three roles with random passwords stored in pgpass, and asks for the superuser password only in a terminal without saving it. It gives specific hints for pg_hba and locale failures.
- **The empty library.** It offers Add a precon, Import cards and New deck. The import preview adds nothing until confirmed and says what it read.
- **Linux.** The systemd service and timer are tested in CI and the Linux-specific help is thorough. `homenet status` is an excellent network checklist.
- **Upkeep.** `update` only fast-forwards, backs up before migrating, checks the Forge build's SHA-256 and runs the smoke test. One `schedule install` covers backups, pruning, restore checks and the export. The card data refreshes itself weekly.

## The 5 highest-leverage changes, in order

1. **Make database failures name their cause.** One change across the doctor, the console, `db status` hints and the page's messages: "nothing answering at host:port, check the service" versus "can't log in, run `db setup`". Add the timeout wording and the Windows postgres password reset to troubleshooting.
2. **Add a "Quick start (Windows)" box to the top of SELF-HOSTING.md.** Say to use PowerShell, link each download, cover the Python PATH checkbox and `python --version` = 3.14, keep the PostgreSQL installer defaults, explain how to check the service is running, then the six commands, and tell people to run the doctor after each step. Move the platform table, WSL and network-range notes, and the Linux server material lower down.
3. **Make config.json mistakes harmless and visible.** Read it as `utf-8-sig` and turn JSON errors into "config.json line L, column C". Warn about an unknown `role`. When there is no config, say so on the console and on the "Who are you?" screen.
4. **Either support macOS properly or narrow what the docs promise.** Fix the smoke test's false backup PASS first, because it is a false all-clear about backups. Then either add stop and restart on macOS (or let `update` skip them), a launchd plist and nightly job example, and the Homebrew superuser steps, or say plainly that macOS is terminal-only and remove the claims made about `scripts/decklab` and `update` there.
5. **Give people without git a working route.** Publish a first release after fixing the config.json fingerprint bug and writing out the full release update steps. Until then, say in README that git is required.
