# Deck Lab

Deck Lab is a self-hosted web app for one household's **Magic: The Gathering** cards (and a small **Pokémon TCG** inventory). Its main job is **building Magic decks and working out which cards to buy for them**.

## This repo is public

- This repo holds Deck Lab's code, tests and docs, and is **public**. The household's own records live in a separate private repo (TradingCardCollection): the real `decklab/config.json` (profiles, emails, the domain, Cloudflare Access), the dated buylists and reports under `magic/`, and `pokemon/`. Here those paths are gitignored: on the PC they may sit in the working tree, but they're never committed to this repo.
- **Never commit personal data here:** no real names beyond Matt's, no email addresses, no real domain or Cloudflare details, no card prices paid. The other people in the docs and tests (user1 to user5) are stand-ins for the real household and members; keep using them, and keep test emails at `example.com`. Copy `decklab/config.example.json` for a new setup.
- The git tags these docs mention (`pre-db-inventory`, `pre-db-decks`, `pre-phase5b`) and links to `magic/` files are in the private repo, not this one.

## What each game is for

| Game | Why it's collected | What that means for your work |
|---|---|---|
| Magic | To **play**, with physical cards only (no MTG Arena). | Judge cards by how well they play, not by collector value. When suggesting purchases, default to the cheapest printing (non-foil, any set) unless the user asks for a particular one. |
| Pokémon | **Full-art singles only**, for the art. The user **never plays** the game. | Don't suggest decks, sealed product, or non-full-art cards. Treat "value" as market price and condition, not playability. |

## How Magic gets played

- **Now: casual 60-card decks, 1v1 at home.**
  - Use normal deck-building rules: at least 60 cards, and at most 4 copies of any card except basic lands.
  - **Ignore ban lists and format legality.** Any card ever printed is fine. Don't reject or flag a card for being banned or rotated.
  - "Competitive" here means the deck is strong and plays well in 1v1, not that it's tuned for a tournament metagame.
- **Later: Commander**, at a local shop's social Commander nights.
  - Commander decks are 100 cards, one copy of each card, and must fit the commander's color identity. The Commander ban list does apply.
  - Aim for the power level expected at social nights. Look up the current Commander Brackets and Game Changers list before recommending cards; don't rely on memory.
- **Shared collection:** the two home players (Matt and User1) use the same card pool. There's no owner column, but each deck records who plays it.
- **Sleeves and storage:** each built deck is sleeved and has its own deck box. All other cards are stored unsleeved in a 4-row storage box that holds about 2,400 unsleeved cards.
  - A product kept intact (its status's `intact` is `yes`; see "Products" below) is stored like a built deck, with its own sleeves and box. One sleeve design and one deck box cover the whole product, even when it holds several decks.
  - A deck's sideboard is sleeved in the deck's sleeves, so swapping cards in between games doesn't show.
  - Several built decks and intact products may use the same sleeves (Matt's decision, 2026-10-13): it's up to the players not to play two of them against each other. Each still needs enough sleeves for its own cards.
  - The sleeves, deck boxes and playmats themselves are Deck Lab's accessories list, in its database (see "Accessories" below). Each is Matt's, User1's or shared, and only its owner sees and changes it (shared: both). A deck records its sleeves and box in its text's `- **Sleeves:** <id>` and `- **Deck box:** <id>` header lines; an intact product records them in its status's `sleeves` and `deck_box`. Both hold an accessory id. Older free text such as `red` is still read, but Deck Lab can't check it.
  - Moving a card between built decks only means changing its sleeve, so swaps are cheap. A card taken out of a deck goes back into storage unsleeved.
- **No budget tracking:** don't track spending, total up what's been spent, or ask what the user paid for things.

## Data formats

### Spaces: `home` and each person's own

- Each profile in `decklab/config.json` has a `role` (`admin` or `member`), a `space` and lowercase `emails`. Matt and User1 share the `home` space: everything else in this file (the shared collection, tokens, decks, products, orders, receipts, accessories, watchlist) is home's. User2, User3, User4 and User5 (`user5`) each have their own space, whose `space` in the config is their profile id: their collection, token cards and decks, all in Deck Lab's database (the inventory and deck commands take `--space <id>`; home is the default). Only home profiles have `plays_as`.
- Home deck ids stay `<kind>/<slug>` (and `product/...`, `pairing/...`); a person's deck id is `<id>/<kind>/<slug>`, such as `user2/casual/elves`.
- Owned vs needed, cards in use in other built decks, and tokens are worked out within the deck's own space. A person's space has no orders, products or accessories, so nothing in it is ever "on the way". Their wishlist is in Deck Lab's database (see "Wishlists and other database data") and is checked against their own space.
- A person's deck has no `Played by` line (it's theirs by its space) and no `Sleeves` or `Deck box` lines; Deck Lab refuses a save that adds them. Otherwise it follows the deck text format below.
- A person's collection and tokens follow the same rules as home's (see "The inventory" below). Don't move cards between spaces: each space is a separate physical collection.
- Who may change what is in `decklab/lib/permissions.py`: an admin edits everything in his own space (every deck, its collection, tokens, tables and games) and, at home, the receipts, orders and products, but nothing in another space (E10-S29, 2026-10-18: on the page Matt can't read or change a member's collection, tokens, decks or games, so upkeep there goes through Claude and the command line, which still writes every space); a member edits their own space, or (at home) the decks Played by them, and User1 home's collection and tokens as Matt can (E10-S43: Collection page edits, imports, Add a precon, the Tokens page). A config where no profile has a `role` treats every profile as an admin. Deck Lab's server checks it on every write (`decklab/lib/api/guard.py`), on the home network too: there the profile picked on the "Who are you?" screen has the same rights as through the tunnel, and only a script naming nobody passes everything (the command line isn't a request: `python -m decklab.db` writes every space, and `--actor` only names who made a change; a member's upkeep, such as a precon, is `collection merge --space` or `collection add-precon --space`). A script is code outside any request (a job thread, a test) or a home-listener request from this PC's loopback (`127.0.0.1` or `::1`) sending `X-Deck-Lab-Script: 1` with no viewer (`guard.script()`; the tunnel's listener, on `127.0.0.1` too, never makes one): a Python script on the PC that calls the API and needs full reads sends that header. Any other request naming nobody (a phone on the Wi-Fi, the PC's browser before a profile is picked) is refused every write and sees only what's open to everyone. "Who are you?" offers only home profiles (Matt and User1), and a home-listener request naming anyone else (header, `?profile=`, `?viewer=` or a body's `profile`) gets 403 "Sign in through decklab.example.com": other members come in only through the tunnel, from the home Wi-Fi too (E10-S35, 2026-10-18). Starting a Forge run follows the simulations setting an admin picks on Deck Lab's Settings page (`#/settings`; admins only by default, anyone, or paused, by role even at home; anyone who can't start a run sees why beside each Play or Start, in words naming nobody, and a member's answer holds only the mode and that reason, never who set it, when or the worker counts: E10-S34), which also limits how many Forge workers the PC uses (`decklab/lib/api/simulations.py`). The mode is kept in the database; while it can't be read, Deck Lab goes by the last mode it read, else admins only. The worker limit is still a file.
- **Who may read the inventory** (`permissions.sees_inventory`, E10-S29, built 2026-10-18): a space's collection and tokens only its own people, home's Matt and User1 and a person's only that person, with no admin override; home's orders, products, watchlist, checks, receipts and packing plan only Matt and User1, never anyone else (`permissions.sees_home_records`). Deck Lab's server answers 403 to anyone else (Shopping, Receive delivery, the Packing plan, and the Collection and Tokens pages and the precon preview for another space), naming no one ("That collection isn't public.", the same as for a space that doesn't exist), and the page hides those pages; a write to another space's collection or tokens gets that same 403 before anything else is checked. Inside those answers a deck the viewer can't see is named only as "one of the home decks" (holders, token uses, missing tokens, the Tables out of date list's held spaces), and pool warnings name no hidden deck nor, to anyone outside home, home's orders and products. The printing picker counts the viewer's own space's copies. On the home network, reads and writes follow the home profile picked on the page's "Who are you?" screen (or the avatar menu's Switch person); a script naming nobody sees everything, and any other request naming nobody none of it. The Game log and Activity show each viewer, an admin too, only the games and rows of their own space; in a game with another space's deck, that side is named only by its space ("one of the home decks", no list), each space changes only its own side, the date, result and notes stay with the space that recorded it, a sideboard plan is only its deck's space's, and a game names only decks its recorder may see (E10-S32, built 2026-10-18). Decks are private to their space (E10-S30, built 2026-10-18; `permissions.sees_deck` / `guard.sees_deck`): a deck's page, list, prose, history, stats, matchups and every other reader of it answer only within the deck's own space (home's decks, products and pairings for Matt and User1; a person's for that person), with no admin override (Matt doesn't see a member's decks), and to anyone else exactly as a missing deck (404 "No deck 'casual/gruul-ramp'", before any 403 or 409); a script naming nobody sees every deck, a space's owner may make its decks Public (E10-S28's switches, `guard.public_deck_spaces()`: read-only to everyone signed in), and a visible Forge run may be stopped by whoever started it, a person with a deck of their own space in it, or an admin (a hidden run only through an admin's anonymous controls). The command line isn't a request: `python -m decklab.db` and `sql` read every space.
- **Private by default** (Matt's decisions of 2026-10-13 and 2026-10-18; design in `decklab/design/privacy-by-default.md` and `decklab/design/member-template.md`, stories E10-S28 to E10-S43, built in the member template's order after 2026-10-19): each space's collection and tokens, decks and Game log, and each accessory owner's kit, will be seen outside their space only when the owner makes them **public** (read-only, to everyone signed in through Cloudflare Access, never the open internet), and an admin won't override that. ### The inventory: in Deck Lab's database

Every space's collection, token cards and raw imports, the orders, the products and the watchlist are rows in Deck Lab's PostgreSQL database (since phase 3 of the move; the decks and accessories are in the same database since phase 4). There are no inventory files in `magic/`: never recreate `collection.csv`, `tokens.csv`, `watchlist.csv`, `orders/`, `products/` or `imports/` there, and never write SQL to change the inventory. The old files are in the git tag `pre-db-inventory`, where links to them from older buylists, reports and deck notes still resolve (`git show pre-db-inventory:magic/watchlist.csv`).

**Reading** (system `python` from the repo root; each command reads one consistent snapshot):

- `python -m decklab.db collection list [--space S]`: a space's collection, as CSV in the columns below (and on stderr its `sha`, which `collection edit --expect` and `collection apply --expect` take).
- `python -m decklab.db tokens list [--space S] [--json]`: its token cards, numbered, with the list's `sha`.
- `python -m decklab.db order list [--pending] [--json]`; `order show ID [--json]` prints a record with each component's numbered rows and checks, and `order show ID --csv COMPONENT` a payload's or product's card list as CSV.
- `python -m decklab.db watchlist list [--state S] [--csv | --json]`: the purchase queue, numbered.
- `python -m decklab.lib.pool <deck-id>` (or `--space S` for a whole pool): owned, on the way and in use. `python -m decklab.lib.purchases --check`: the orders and the queue checked.
- `python -m decklab.db inventory export DIR`: everything as the old files (`collection.csv`, `tokens.csv`, `watchlist.csv`, `products/` with `status.csv`, `orders/` with `records/`, `people/<id>/`, each space's `imports/`) in `DIR/magic`, for reading a lot at once. Use a new folder in the scratchpad, never the repo, and never edit what it writes: it's a copy.
- `python -m decklab.db sql "select ..."` (read-only): `collection_card`, `collection_import` (+ `collection_import_content`), `token_card`, `product`, `product_item`, `product_status`, `purchase_order`, `order_component`, `order_card_item`, `order_token_item`, `watchlist_item` and `inventory_revision`.

**Command-line actor:** for your own data writes, add `--actor matt` (or another configured profile id) after the write subcommand. Activity names that profile, from the command line. Assistant writes omit it and remain Claude's. Unknown actors are refused; the option changes attribution, not PC access. It applies to inventory, decks, accessories, images and wishlists; maintenance commands keep their system actors.

**Changing:** only with the commands below, or on Deck Lab's pages. Every write needs a non-blank `-m "<what and why>"`, and a removal or cancellation a `--reason`; each is one change set by Claude by default in the audit trail (shown on the Activity page), and nothing is committed to git for it. The order, product and watchlist writes take `--dry-run`. A write that changes what decks count as on the way or in use (an order added, edited, split, cancelled, removed or marked as extra copies, a product added or kept intact or broken up, a receipt) also refreshes the decks' owned-vs-needed tables in the same change (only the decks of the spaces it touches, so a home receipt never rewrites a person's deck), and its preview lists the decks it would rewrite. The order and product commands refuse a change after which the tables couldn't be refreshed (see "Placing an order"); if the refresh still can't be worked out when a change is saved (an unknown card in a deck or the pool, a deck without a table), the change is saved anyway and the decks are left as they were. Card names are checked against the card index (run `python -m decklab.lib.cards update` first on a fresh clone). Exit codes: 0 done (or previewed, or nothing to change), 1 refused, 2 the database can't be reached, 3 saved but the deck tables couldn't be refreshed: stderr says why, and the change itself stands (fix the cause, then `deck tables --apply`, see "Decks"). Files you hand to a command go in the scratchpad.

#### Collection cards

Their columns, also those of any cards CSV given to `collection merge`, `order add --cards`, `order edit` or `receive --rows`:

```
name,set,collector_number,finish,quantity,condition,language,notes
Llanowar Elves,fdn,227,nonfoil,2,NM,en,
```

- **Identity key:** `(set, collector_number, finish)`. When the same key comes up again, add to its `quantity` instead of adding a second row.
- `name` is the exact Scryfall card name. Double-faced cards use `Front // Back`.
- `set` is the lowercase Scryfall set code (`fdn`, `fdc`, ...). `finish` is `nonfoil` | `foil` | `etched`.
- Unknown condition or language stays blank; never assume Near Mint or English during an import. If copies of one printing have different or partly unknown conditions/languages, the merged field stays blank and its notes flag that ambiguity; the identity key does not separate those copies.
- Include basic lands only if they're special (full-art, foil). Assume the user has plenty of plain basics.
- **Cards that come from nowhere Deck Lab records** (a scan, a trade, a gift): `python -m decklab.db collection merge FILE [FILE ...] [--space S] -m "..."`, each FILE in the columns above (or a product list's). It checks every row and name first, then adds the quantities on the identity key (ordinary basic lands left out unless that printing is tracked; a condition or language the copies don't share goes blank with a note), and keeps each file unchanged as one of the space's raw imports. Recorded orders and products never go this way: they arrive through `receive`. Merging the same file twice adds it twice. It doesn't refresh the deck tables: it prints the space's decks whose tables are now out of date and the command to run, `python -m decklab.db deck tables --apply -m "..."`, or, when that would refuse, every problem in its way (on Deck Lab, the Decks page's **Tables out of date** list has them, with **Update all**).
- **A published precon** (the cards a precon came with, in no recorded order): `python -m decklab.db collection add-precon CODE [--space S] [--title T] [--played-by user|wife|either] -m "..." [--dry-run] [--add-tokens] [--token-rows FILE --tokens-source-sha256 SHA]`, the Collection page's **Add a precon** from the PC (the same code, so the same cards and deck), for upkeep in any space, a member's included (E10-S36). CODE is MTGJSON's file name for the deck, which `collection precons [WORDS]` lists (such as `KeenEngineering_FDC`). `--dry-run` prints the cards it would add (plain basics left out, condition and language blank) and the deck it would make. Without it, the cards and the built deck (its title the commander and precon's name unless `--title`; at home Played by `--played-by`, else the `--actor`'s `plays_as`) are saved in one change, the deck's table worked out with those cards added, and the raw import kept. A title whose deck name is taken in that space is refused with the existing deck's id: give another `--title`. Its last line gives the counts added and the deck's id: for a member's space, tell Matt only that and that it's done, never the list. Like `collection merge` it names other decks whose tables are now out of date. Exit codes as the other inventory commands (0 done or previewed, 1 refused, 2 the database can't be reached).
- Deck Lab's Collection page edits a space's collection too, for that space's own people only (home's: Matt and User1; a member's: only that member, never Matt as an admin since E10-S29, so for a member's space use `collection merge --space`, `collection edit --space`, `collection apply --space` and `collection add-precon --space` (E10-S36) on the PC when the member asks, directly or through Matt, and report only counts): adding, changing or removing single cards, importing a ManaBox, Moxfield, Deckbox or collection-columns export (its upload kept as a raw import), the Card list's **Set condition & language…**, which sets one condition and/or language on every row the search and filters show (only blanks by default) as one change, and **Add a precon**, which adds a published precon's cards (MTGJSON's list) and makes its built deck, in one change (its table worked out with those cards already added); the precon's token cards are skipped by default. **Add its token cards too** offers explicit physical quantities per source entry: unknown counts remain blank, 0 skips an entry, and an ambiguous entry needs one checked front choice. Count a physical card only once across paired-face entries, setting the other entry to 0. Each positive entry stays a separate row with printing, finish and reverse face unknown; no pair or extra card is inferred. On the PC `--dry-run` prints public options and their full source SHA; `--add-tokens --token-rows FILE --tokens-source-sha256 SHA` takes UTF-8 CSV `source_row,front,quantity` with every offered entry exactly once and 0 for explicit skips. The source SHA binds row meanings; the confirmation file and MTGJSON cache are unchanged. Without a choice file, `--add-tokens` still supports a fully declared unambiguous batch. Malformed or unchecked names block only the optional tokens, not the playable precon. **One row from the PC:** `python -m decklab.db collection edit SET NUMBER FINISH [--space S] [--quantity N] [--condition C] [--language L] [--notes T] --expect SHA -m "..." [--reason R] [--allow-in-use] [--dry-run]` changes only the fields given (`""` clears one; condition NM, LP, MP, HP or DMG, language Scryfall's code) as the page's card sheet does, as one change. `--expect` is the sha `collection list` prints on stderr (at least its first 12 characters). `--quantity 0` removes the row and needs `--reason`: ask the user why first when cards are sold or traded. A reduction leaving fewer copies than built decks or intact products hold is refused unless `--allow-in-use` (check with the user first). `--dry-run` prints the row before and after and the decks whose tables it would leave out of date. A different printing or finish is still the page's (or a removal and a merge). **Many rows from the PC:** `python -m decklab.db collection apply FILE [--space S] --expect SHA -m "..." [--reason R] [--allow-in-use] [--remove-missing] [--dry-run]` makes the collection match FILE, an edited copy of `collection list`'s whole output in the scratchpad, as one change: rows are matched on the identity key, each changed quantity, condition, language or notes is checked as `collection edit` checks it, and a row at quantity 0 is removed (needs `--reason`). A row left out of FILE is refused, naming how many, so a cut-off, filtered or header-only copy never removes the rest; keep every row (or set the ones to remove to 0), and give `--remove-missing` only when every row left out really should go. It never adds a row: a key the collection doesn't have, a changed name or a key listed twice is refused (new cards go through `collection merge`). `--expect`, `--allow-in-use` and `--dry-run` (which lists every change) are `collection edit`'s, and the listing as printed changes nothing. Use it rather than many `collection edit`s, such as setting a precon's cards to NM and `en`. On the Collection page a removal can carry a reason (optional); ask the user to enter why when cards are sold or traded. The page's changes don't refresh other decks' tables either (the page says how many are out of date and links to the Decks page's **Tables out of date** list, where **Update all** refreshes them): or run `python -m decklab.db deck tables --apply -m "..."`.
- **A trade** (cards that left and cards that came in, as one change, E7-S22): `python -m decklab.db collection trade --out GAVE.csv --in GOT.csv [--space S] [--with T] -m "..." [--allow-in-use] [--dry-run]`. `--out` lists the copies given (at least `name,set,collector_number,finish,quantity`, matched on the identity key, never more than the row has), `--in` the cards got in the collection's columns, checked and merged as `collection merge` does (no raw import kept). The change set's message is `-m` plus both sides and the `--with` note, its reason `Traded` (or `Traded with T`); never add prices. Copies built decks or intact products hold are refused without `--allow-in-use` (check with the user first), `--dry-run` names the decks that lose cards, and like merge it names the tables left out of date afterwards. Ask the user before recording one, as for any removal. The Collection page has no trade yet: there a trade is still a removal (reason Traded) and a separate add.

#### Token cards

Their columns, also those of any tokens CSV given to `order add --tokens`, `order edit` or `receive --rows`:

```
front,back,set,front_collector_number,back_collector_number,finish,quantity,front_details,back_details,notes
Dog,Beast,,,,,1,,3/3,User-reported owned; unspecified characteristics and printing unconfirmed
```

- This is the owned token/reminder inventory, separate from playable cards. `quantity` counts physical cards, not faces. A double-sided card can represent only one of its faces at a time; two Rabbit/Rabbit cards are two available markers, not four.
- Preserve the reported front/back pairing. Use exact Scryfall face names, including reminder names such as The Monarch. Store known power/toughness, colour and abilities in the relevant details field; leave unreported characteristics and printings blank rather than guessing from a token's name or likely product.
- Keep different variants separate even when their face names match. Do not merge rows across an unverified printing or ability difference. Rows are kept sorted by set and collector numbers where known, then front/back names and details.
- **Details** are `;`-separated parts, such as `1/1; green; flying, deathtouch`. Write `no lifelink` for an ability the card lacks, and `colour unconfirmed` (or `P/T unknown`, `abilities unspecified`) for a part not checked. Anything else (a type line, rules text, a printed colour that isn't a Magic colour such as `printed pink`) is kept but never compared. Only details count when Deck Lab matches a card to a deck's token; notes never do.
- **Changing them:** Deck Lab's Tokens page (`#/tokens`), or `python -m decklab.db tokens add|edit|remove`:
  - `tokens list` numbers the rows and prints the list's `sha`. `tokens edit ROW --expect SHA [options] -m "..."` and `tokens remove ROW --expect SHA -m "..." --reason "..."` need that sha (its first 12 characters will do), so ROW always names the row of that listing; if the list has changed since, nothing is written: list it again. `tokens add --front F --quantity N [options] -m "..."` may give `--expect` too (`none` for a space with no token cards yet).
  - The options are `--back`, `--set`, `--front-number`, `--back-number`, `--finish`, `--quantity`, `--front-details`, `--back-details` and `--notes`; an edit keeps every column it isn't given, and `""` clears one. Names must be Scryfall token, emblem or reminder faces, and are fixed to their exact spelling.
  - Rows are never merged. A row naming a card another row names is refused unless `--separate`, which is allowed only when either row isn't fully known (as receipts keep unverified variants apart). To combine two fully known rows, raise one's quantity and remove the other.
- `python -m decklab.db tokens check [--space S]` (the same as `python -m decklab.lib.tokens --check`) reports rows that break these rules: face names that aren't Scryfall token, emblem or reminder names, printings that aren't that face, a blank back without `single-sided verified`, and problems in pending token orders. It exits 1 if there are any, and without the card data it skips the name checks with a note. After them it warns, without failing, about details parts it can't read that look like mistakes: a P/T, colour or keyword missing its `;` (`4/4 white flying`, with the rewrite `4/4; white; flying`) or a near-miss spelling (`whte`: did you mean white?). It also warns about a row built decks (and intact products) want more cards of than it has, naming them: a deck with a Token cards line wants what the line packs, any other built holder at least one of each row it uses; decks still being built don't count. It warns about a Token cards part no token card matches too. The Tokens page marks such a row **Too few for N built decks**, and a deck page's Tokens part names the other built decks beside the card.
- Token inventory changes never alter decklists, the playable-card pool, the watchlist or order checks. Incoming product tokens aren't owned until they're inspected: record that work in the product component's `checks`, and on arrival add the actual physical cards (pairing and quantity) with `tokens add`.
- Token cards a built deck packs (its Token cards line, see "Tokens" under Workflows) are in use for the space's other decks.
- The tokens each deck needs come from Scryfall's `all_parts` links between cards and tokens, so they're approximate. Tokens made only through rules text and most token copies of other cards aren't detected, some listed tokens appear only in certain modes or for the opponent, and Deck Lab never says how many a game needs.

#### Orders

- An order is a record with components that may arrive separately; its overall status is derived from them. The record has `id` (`YYYY-MM-DD-<topic>`), `seller`, `ordered_on`, `sources` (repo-relative buylist or deck paths), `notes` (useful to the person checking the delivery) and optionally `audit_notes` (provenance, never shown as shopping notes). Unknown seller or dates stay blank. **Never store prices or spending totals.** Components in one known shipment share a record; do not infer that different sellers or unrecorded historic acquisitions were one order.
- Each component has an `id` (`cards`, `tokens`, or a product's stem), a `kind` (`cards`, `tokens` or `product`), a `status` (`pending`, `received` or `cancelled`), `received_on`, and `checks` (unresolved physical checks); a verified receipt moves the checks it completed into `verified_checks`. A cards component's rows are in the collection's columns; token/reminder singles always go in a `tokens` component, in the token cards' columns, never with the playable cards. Card-specific facts and unresolved printing, finish or condition details go in a row's notes.
- Pending cards aren't in the collection. Count them as available when planning decks, but label them "on the way". A cancelled component is kept, with its reason in `audit_notes`, and never counts as incoming.
- A populated `checks` list on a pending or received component is unfinished inspection work, including checks on a received product's tokens; keep it until the physical facts are confirmed. A cancelled part retains its checks only as history.
- Placing, fixing and receiving orders: see "Placing an order" and "Logging new cards" under Workflows.

#### Products

- A sealed product owned or ordered has a fixed card list (columns `name,set,collector_number,finish,quantity`, optionally `section` (`commander`, `deck`, `sideboard`, ...) or `deck` (each deck's name, for a product holding several), `rarity` and `notes`), a display name and format, and a status: `status` (`owned`, `preordered`, `ordered` or `cancelled`), `intact` (`yes` or `no`, blank until it arrives), `sleeves` and `deck_box` (accessory ids, see "Accessories"; only for an owned product kept intact) and `notes`. A list with a `section` or `deck` column is played as decks. The list is reference only: the collection is what's owned.
- A product kept intact holds its cards like a built deck, so they aren't free for other decks. After arrival, its deck Overview's **Product storage** panel previews **Break up into storage** or **Keep intact**, then asks for confirmation. Breaking up clears its sleeves and deck box and frees its cards; keeping intact reserves its existing collection copies (only a product with deck lists). The storage state, kit removal and affected deck tables save in one change; an unexpected table-refresh failure is reported with a **Tables out of date** link. The page follows home inventory and product-edit permissions and does not let an admin clear another owner's private kit. On the PC, `python -m decklab.db product set-intact STEM no -m "..."` breaks it up; `yes` keeps it intact. Choose its kit on Deck Lab or with `product set-kit` below.
- A product is added with its order (`order add --product`, see "Placing an order"), or to an existing order with `product add STEM --order ID --csv FILE [--name N] [--format F] [--status ordered|preordered] [--notes T] -m "..."`. Correct a pending product with `product edit STEM [--csv FILE] [--name N] [--format F] [--status ordered|preordered] [--notes T] -m "..."` (`--dry-run` previews), or Shopping's **Edit order… > Correct product…**. Only supplied fields change; `--csv` replaces its complete list, retaining optional section/deck columns. Its stem and order component stay fixed; affected deck tables refresh in the same change. Correction refuses owned, received or cancelled products. A pending product can be cancelled through its order: its list stays as history with status `cancelled`, excluded from incoming supply and the deck library. Removing an unreceived mistaken order removes its products and payloads too. A pending product arrives through `receive ... --intact yes|no`: its playable cards are added (plain basics left out) and its status becomes `owned`. Its token checks stay open until its physical tokens are recorded.

#### The watchlist (purchase queue)

Its columns, as `watchlist list --csv` prints them and `watchlist apply --csv` reads them:

```
name,set,collector_number,finish,quantity,for,printing,listed_aud,listed_at,in_stock,checked,notes,state,source
Clifftop Retreat,frc,67,nonfoil,2,The Free Peoples,any,0.50,Ronin Games,no,2026-10-05,the new Reality Fracture Commander copy,waiting_for_stock,magic/buylists/2026-10-05-stardew-and-tolkien-decks.md
```

- This is the current intended-purchase queue, separate from personal wishlists and historical buylists. `quantity` is the number still intended to buy, after confirmed orders; do not put ordered or received copies here.
- `state` is `ready`, `waiting_for_stock`, `waiting_for_reprint`, `deferred` or `long_term`. Use `source` for a repo-relative research path explaining the decision, or a deck's old path (`magic/decks/<kind>/<slug>.md`, `magic/people/<id>/decks/<kind>/<slug>.md`, in exactly that case), which is still accepted for a deck that exists in Deck Lab (the same goes for wishlist and order sources). A ready row means intended to buy, not a claim of live retailer stock.
- `long_term` rows are the broad plan: cards for decks the user has decided to build later (such as a planned Commander deck), bought opportunistically to share postage with other orders rather than urgently. Add them when the user agrees to a long-term plan; still don't promote favourites, wishlist entries or speculative upgrades on your own. Promote a row to `ready` when its deck becomes the next one to build.
- `printing` is `exact` when only that printing will do (bought for its art, like the Stardew Valley Secret Lair cards), or `any` when any printing plays the same. For `any`, `set` and `collector_number` name the printing to look for and can be blank.
- `listed_aud` and `listed_at` are the lowest price seen and the shop listing it, whether or not it had stock; `in_stock` says whether it did on the `checked` date.
- Token/reminder cards can be queued too, using their exact Scryfall face name and token set code (`tltc`, ...); say it's a token card in `notes`. Once ordered they go in the order's `tokens` component.
- **Changing it:** a row is selected by `NAME`, `NAME@FOR` (its `for` column) or `#N` (its number in `watchlist list`).
  - `python -m decklab.db watchlist set --add --name N --state S [--set --number --finish --quantity --for --printing --notes --source ...] -m "..."` adds a row; `watchlist set SELECT [--quantity Q] [--state S] [--listed-aud A --listed-at SHOP --in-stock yes|no --checked YYYY-MM-DD] [...] -m "..."` changes one; `watchlist remove SELECT -m "..." --reason "..."` removes one.
  - After a shop check, `watchlist list --csv > <scratchpad>/queue.csv`, update the copy's prices, stock and `checked` dates, then `watchlist apply --csv <scratchpad>/queue.csv -m "..."` makes the queue match it in one change.
  - When queued copies are ordered, `order add --fulfils` reduces or removes their rows in the same change. Preserve unrelated quantities; if the printing preference is `exact`, only that printing fulfils it.

### Decks: in Deck Lab's database

Every space's decks are in Deck Lab's database (since phase 4 of the move): each deck is its whole Markdown text (the format below), with every saved revision kept. There are no deck files: never recreate `magic/decks/`, `magic/people/<id>/decks/` or a deck `.md` anywhere in the repo, never bring a pulled copy back into it, and never write SQL to change a deck. The old files are in the git tag `pre-db-decks`, where links to them from older buylists, reports and deck notes still resolve (`git show pre-db-decks:magic/decks/casual/gruul-ramp.md`); their revisions up to then were imported into each deck's history.

A deck's id is `<kind>/<slug>` at home (`casual/gruul-ramp`, `commander/giada-angels`) and `<id>/<kind>/<slug>` in a person's space (`user2/commander/lathliss-reign-of-dragons`). The slug is lowercase letters, digits and single hyphens, unique in its space across both kinds (ignoring case), and changes only through a rename on Deck Lab's deck page (More, **Rename deck…**, E1-S19): the id follows the new title, and the old id stays reserved as an alias, so old links, history and sources still resolve. The command line has no rename. An unbuilt deck can also be retired (More, **Retire deck…**) and restored from its History. A title change in the text alone (the `# ` line) keeps the id.

**Reading** (system `python` from the repo root; each command reads one consistent snapshot):

- `python -m decklab.db deck list [--space S] [--json]`: each deck's id, title, kind, status, who plays it, its revision, the date of its "Decklist changed" line when it has one, and whether its owned-vs-needed table is out of date.
- `python -m decklab.db deck show ID [--version target|owned] [--json]`: the target list, or the substitute list.
- `python -m decklab.db deck pull ID -o <scratchpad>/ID.md`: the text, byte for byte (LF), then `revision N` and `sha <sha256>`, the token `push` needs. Without `-o` the text goes to stdout. `deck pull --all -o <scratchpad>/decks` writes every deck as `<id>.md` in that folder. A path inside the repo's old deck folders is refused.
- `python -m decklab.db deck history ID` lists the saved revisions, newest first, with who, when and the whole message (a deleted deck's too); `deck revision ID N [-o FILE]` prints one revision's text. The deck page's More, **History**, shows the same, for a deck that exists, each revision against the one before it.
- `python -m decklab.lib.pool ID` (owned vs needed), `python -m decklab.lib.tokens ID`, `python -m decklab.lib.stats ID`, and the Forge commands take deck ids as before.
- `python -m decklab.db sql "select ..."`: `deck` (id, space_id, kind, slug, title, status, played_by, revision), `deck_text` (each deck's text), `deck_revision` (every revision: revision, at, actor, message, op `A`/`M`/`D`, git_commit for one imported from git, text), `deck_line` (each list line, worked out from the saved text: version `target`/`owned`, section, position, quantity, name, set_code, collector_number, finish) and `decks_revision`. **Which decks use a card:** `python -m decklab.db sql "select d.id, d.status, l.version, l.section, l.quantity from deck_line l join deck d on d.id = l.deck_id where l.name = 'Llanowar Elves' order by d.id"`.

**Changing:** only with these commands or on Deck Lab's pages. Every write needs a non-blank `-m "<what and why>"` (a deletion also `--reason`; `deck tables --apply` has a default message) and is one change by Claude by default in the audit trail and the deck's history; nothing is committed to git. Write the file you push in the scratchpad.

- **`python -m decklab.db deck push ID FILE --expect N -m "..."`** saves FILE as the deck's whole text. `--expect` is the revision (or at least the first 12 characters of the sha) `deck pull` printed: if the deck was saved since, nothing is written, so pull it again and redo the change on the new text. The file is read as UTF-8 (a byte-order mark dropped, CRLF made LF), at most 1 MiB, and must parse as a deck with a `## Decklist` block and a title of 1-100 characters; a person's deck can't gain `Played by`, `Sleeves` or `Deck box`. Push writes the text exactly as given: it doesn't add the "Decklist changed" line and doesn't re-render Deck Lab's parts (the table, its labels, its prices). Changed `Sleeves` or `Deck box` lines are chosen as the deck page's picker chooses them, in the same change: an id of an accessory the deck's player may use, on a built deck (sleeves other decks or intact products use are fine; a deck box only while one is free) (an older free-text value may stay as it is, but can't be newly written). Afterwards it prints what to look at: an out-of-date table, card names that aren't Scryfall's, the token cards the deck makes, and what `accessories check` reports about the deck.
- **`python -m decklab.db deck new KIND SLUG --from FILE [--space S] -m "..."`** makes a deck (home's by default) from FILE, read and parsed as `push` reads it. Of push's `Sleeves` and `Deck box` rules it checks only that an id is an accessory the deck's player may use (not that the deck is built, or the deck box's quantity), so write a new deck without those lines and give it its sleeves and deck box with a later `deck push`.
- **`python -m decklab.db deck delete ID --expect N -m "..." --reason "..."`** deletes a deck; its history stays. A built deck holding sleeves or a deck box is refused: push it first with its status back to `building` (or `idea`) and without the `Built version`, `Sleeves` and `Deck box` lines.
- **`python -m decklab.db deck tables [ID ...] [--reprice] [--check | --apply] [-m "..."]`** works the owned-vs-needed tables (and the substitute lists' arrival notes) out again from the inventory for the decks named, or every deck: without `--check` or `--apply` it lists the decks whose tables would change, `--check` exits 1 when any would, and `--apply` saves them in one change (all of them, or none if one was saved meanwhile). `--reprice` also prices them with today's card prices and exchange rate, as Deck Lab's **Update the table** (a deck page's Cards tab) , **Update their tables** (offered after a page save leaves other decks' tables out of date) and **Update all** (the Decks page's **Tables out of date** list, of every out-of-date table) do. It never changes a decklist or hand-written notes. It refuses while any space's pool is incomplete (an unknown card, a warning) or a deck can't be worked out (no table, no decklist, an unknown card name), and then lists every problem.

**Workflows on a deck's text:**

- **Editing prose or a list:** `deck pull`, edit the copy, `deck push --expect N`. After a change to a decklist, a status or a `Built version`, run `deck tables ID --reprice --apply -m "..."` so its own table matches with today's prices; `push` says when that deck's own table is out of date. `deck tables ID` touches only the decks named, so after a change to a built deck's list, its status or its `Built version` also run `python -m decklab.db deck tables --apply -m "..."` (no ID) for the other decks whose cards in use changed; push (and `deck new`) names those of the deck's space that are now out of date, with that command or what would make it refuse.
- **"Decklist changed in Deck Lab on <date>; prose sections may be out of date."** in a deck: pull it, update the prose sections to match the decklist, remove that line, and push it. `deck list` shows which decks have the line.
- **A new deck:** write its text in the format below, with an `## Owned vs needed` heading and the table's header and `|---|` lines but no rows yet, then `deck new`, then `deck tables ID --reprice --apply` to fill and price the table (and, if the new deck is built, `deck tables --apply` with no ID for the other decks). Every deck needs that table and only Scryfall card names: one deck without them makes every receipt's and order's table refresh in its space fail.

**Physical box checks:** Build decks' **Check box** reviews an ordinary home built deck's saved physical assembly, every section and basic land included, with installed named or unspecified stand-ins. Counts and section-aware missing/extra differences are local to the review. **Save check date** changes only the optional `- **Box checked:** YYYY-MM-DD` header through a conflict-checked deck save; no observations enter the deck text, inventory or audit message. Its private deck-page date is historical, not a certificate of current contents or printing. The lists, kit, reservations and shared packing ticks are unchanged. When the box differs, the difference review's **Correct the recorded box** previews the corrected physical build (its cards per section, the cards it frees for other decks or newly holds, any the collection can't cover, and the packed token cards, which stay as written) and, after **Save corrected box**, saves that build and the check date as one conflict-checked deck save (`POST /api/deck/box-repair`): the `Assembled` snapshot and installed stand-ins follow the counts (recorded printings kept up to their copies; further copies unprinted), so what the deck reserves matches the box, and other decks' out-of-date tables are listed as after any save. The Planned and Play-now lists, the collection, the kit and the Token cards line are never changed by it. Member and product box checks remain future work.

#### The deck text format

Each deck's text has these parts, in this order:
1. **Header:** archetype, who plays it (user / wife / either), status (`idea` / `building` / `built`), and for Commander decks, the target bracket. A built deck whose text has both a target list and an owned-only list also gets a `- **Built version:** target` or `- **Built version:** owned-only` line, saying which one is physically put together. A built deck also gets a `- **Sleeves:** <id>` line and a `- **Deck box:** <id>` line, each holding an accessory id (see "Sleeves and storage" above). Taking a deck apart (status back to `building` or `idea`) removes both lines. Any deck may have an optional `- **Cover card:** <exact Scryfall name>` or `- **Cover card:** <exact Scryfall name> (SET) <number>` line, the card whose art is its library picture (with a printing, that printing's art); it's also shown small beside the title on the deck page. Without it the picture is automatic: the commander, else the non-land with the most copies in the target list (a creature on a tie). Deck Lab keeps the line as written: only its picture picker (the deck page's More, **Change library picture…**, or the library's More, **Choose deck pictures**) writes or removes it, as one saved revision. The name must be Scryfall's exact name; a line Deck Lab can't use (a name that isn't Scryfall's) falls back to automatic. By hand: `deck pull`, add the line with the other header lines, `deck push`.
   A built deck may have a `- **Token cards:** <count> <faces>[ (SET) <number>]; ...` line, the token cards it packs (see "Tokens" under Workflows). Deck Lab keeps it as written (a page save, `deck tables` and a table refresh don't touch it); Finish building fills it when it's missing, the deck page's packed token sheet rewrites it, and a deck taken apart loses it.
   A built home deck may have a `- **Printings in box:** <count> <name> (SET) <number>[ foil|etched]; ...` line, which physical printing of its cards is in its box (2026-10-27, E11-S30 slice 13): Build decks' **Which printing?** on each pull tile, written by Finish building, or the deck page's **Printings in box…** on its Cards tab (POST `/api/deck/printings`), or `deck pull`/`deck push`. It may be partial (a card it doesn't name isn't recorded) and never names basic lands. It reserves nothing: cards are still counted by name. A save is refused when the line names a card the box doesn't hold, more copies than it holds, or a printing the collection doesn't have of that card, or when the built decks would then record more copies of a printing than the collection has. A later collection edit or repack may make a record impossible; it stays as written, the impossible part is ignored, and the deck page says "Printings in box out of date" (`db check` warns too). Collection then counts the recorded copies exactly ("Recorded in the box"), and Build decks' picker leaves out printings whose copies are all recorded in boxes. Taking the deck apart removes the line; a person's deck can't gain one.
   An optional `- **Usual opponents:** <deck-id>, <deck-id>` header line records the decks in the same space usually played against this one. The Overview's **Choose usual opponents** sheet changes only this deck's line; reverse links are derived when reading. A normal editor or table save preserves it. Deleted or unreadable opponents are omitted from links and picker suggestions.
2. **Decklist** in a fenced block using the Arena/MTGO export format. Commander decks put a `Commander` section first.
   ```
   Deck
   4 Card Name (FDN) 123
   ...

   Sideboard
   2 Card Name (SET) 45
   ```
   Optionally, a `## Considering` heading straight after the Decklist section, with its own fenced block of card lines in the same format but no section headers: cards that might go in the deck (E2-S23). They aren't in either list, so nothing counts them: no owned-vs-needed table, pool, in-use count, packing plan, tokens, stats, Forge list, sleeve count or box check. Deck Lab keeps the block as written on every save and table refresh; the deck page's Cards tab shows it read-only, with the copies free in the pool. Change it with `deck pull`/`deck push` for now.
3. **Owned vs needed:** a table of each card with the quantity needed, owned, and missing, plus an estimated cost in AUD. Its header is `| Card | Need | Owned | Missing | ~AUD each | ~AUD missing | Notes |`.
4. **Substitutes:** cards already owned, or cheaper ones, that could replace expensive missing cards, noting what each swap costs the deck in strength.
5. **Notes:** game plan, mulligan guidance, and a sideboard guide once one exists.

Deck Lab rewrites only the parts it owns (on a page save, "Update their tables", `deck tables` and an inventory change's table refresh) and keeps everything else as written:
- the header fields Format, Archetype, Played by, Status, Built version, Target bracket, Sleeves and Deck box (a `Cover card` line isn't one of them: a page save, `deck tables` and a table refresh keep it as written, and only the picture picker changes it);
- the decklist blocks;
- the owned-vs-needed table's rows and total row. The table always describes the target list, never the owned-only one;
- its own labels at the start of a Notes cell: `1 on the way (order 2026-09-29-shop-a)`, `1 on the way (Wretched Ranks, preordered)`, `2 in use in Gruul Ramp` and, on the total row, `not counted, no price: ...`. Each label is one `; `-separated part. The older `on the way (Wretched Ranks precon)` form counts too;
- the rate in the paragraph above the table, in exactly this wording: `1 USD = 1.4237 AUD (ECB rate of 2026-09-28), pulled 2026-09-28`. If a table has no rate statement, Deck Lab adds one. If the rate is worded any other way, Deck Lab refuses to reprice the table rather than contradict it. Rates elsewhere in the prose belong to the prose and aren't updated.

So that Deck Lab can find these parts:
- Keep the header lines together under the title as `- **Key:** value`.
- Put the target list in a fenced block under a `## Decklist` heading. A text without one is refused by `push` and `new`.
- Put a Considering list in a fenced block under a `## Considering` heading (level 2, the exact word), card lines only.
- Put the substitute list under `### Substitute version (owned and incoming cards)`. Deck Lab also reads the older `### Owned-only version` heading; its internal version key remains `owned`. Incoming copies must arrive before the list can be assembled.
- Write hand notes after Deck Lab's labels, and don't start them in a label's exact form. Hand notes like `on the way (eBay order, due 2026-10-05)` are kept.

Deck Lab's pages call the target list the **Planned list** and the substitute (owned-only) list the **Play-now list**, and so do its warnings. Only the words shown changed: the text's headings, the `Built version` values (`target`, `owned-only`), the version keys (`target`, `owned`) and the commands' `--owned` stay as they are.

### Accessories: in Deck Lab's database

The owned sleeves, deck boxes and playmats and their pictures are in Deck Lab's database (since phase 4; the old `magic/accessories.csv` and `magic/accessories/images/` are in the tag `pre-db-decks`). On the Sleeves & boxes page (`#/accessories`), Add and Edit offer **Photo from this device** as well as **Find picture** from a link. Choose a JPEG, PNG or WebP of at most 4 MiB, preview and crop it, then Save: the row and picture save together. Choosing or cropping alone writes nothing, and Cancel discards the selection. Oversized or invalid pictures are refused without changing the stored row or picture. Saved pictures use the same crop controls later. On the PC use these commands, never SQL:

- `python -m decklab.db accessories list [--json]` prints every row (the command line sees every owner's) and the list's `sha`; `accessories show ID` one row and what holds it; `accessories check` (the same as `python -m decklab.lib.accessories --check`) the rules below that are broken (unknown or wrong-kind ids, owners that aren't a home profile or `shared`, a deck using another owner's accessory, missing or orphan pictures, too few sleeves, deck boxes over their quantity or too small for their deck, lines on decks that aren't built), exiting 1 if there are any.
- `accessories add --kind K --name N [--owner O --brand --colour --quantity --capacity --crop --link --image-source --notes] --expect SHA -m "..."`, `accessories edit ID [options] --expect SHA -m "..."` (columns not given stay; `""` clears one) and `accessories remove ID --expect SHA -m "..." --reason "..."`. `--expect` is the `sha` from `accessories list` (at least 12 characters; `none` before there are any rows): a change to a list that changed since is refused. The owner is `shared` and the quantity 1 unless given. `add` prints the new row's id (also in `accessories list`); a picture comes only afterwards, with `image put <id>.<ext>`, since a picture for an id with no row is refused.
- `python -m decklab.db image put <id>.<jpg|png|webp> FILE -m "..."` stores a picture for that row (its bytes must be that format, at most 4 MiB) and sets the row's `image` (replacing an older picture; the crop is cleared when the picture's name changes, but a picture replaced under the same name keeps it: clear it with `accessories edit ID --crop "" --expect SHA -m "..."`); `image remove NAME -m "..."` takes it away.
- A deck's sleeves and deck box are its text's `Sleeves` and `Deck box` lines (chosen on its deck page or with `deck push`); an intact product's are chosen on the deck page, the Sleeves & boxes page's **Products kept intact** panel, or with the commands below.
- `python -m decklab.db product kit STEM [--json]` prints the product's status, current kit and the products status-list `sha256`. `python -m decklab.db product set-kit STEM --expect SHA [--sleeves ID|none] [--deck-box ID|none] -m "..." [--actor PROFILE] [--dry-run]` chooses one or both fields for an owned product kept intact. Give at least one kit flag; an omitted field stays as written and `none` clears one. `--expect` takes the full SHA or its first 12 characters and is checked again under the write lock. New choices are shared accessory ids of the right kind; the command refuses free text, another owner's accessory and an unavailable deck box. Both fields save as one audited `kit.set` change; `--dry-run` validates without saving. `--actor` changes attribution as for the other accessory commands; omit it for assistant writes.
- `python -m decklab.db sql`: `accessory` (one row per accessory, the columns below) and `accessory_image` (file_name, size, sha256 and the bytes). The command line and `sql` see every owner's rows; keep what you read of another owner's to the user who owns it.

Each row has these columns (`accessories list --json` prints them):

```
id,kind,owner,brand,name,colour,quantity,capacity,image,crop,link,image_source,notes
dragon-shield-matte-black,sleeves,matt,Dragon Shield,Matte,black,100,,dragon-shield-matte-black.jpg,,https://shop.example/p/1,https://cdn.example/1.jpg,
ultimate-guard-boulder-100-black,deck_box,shared,Ultimate Guard,Boulder 100+,black,2,100,ultimate-guard-boulder-100-black.webp,"0.1,0,0.8,1",https://shop.example/p/2,https://cdn.example/2.webp,
```

- `id` is a lowercase slug of at most 40 characters (letters, digits and hyphens, not starting or ending with a hyphen), made once from brand, name and colour, with `-2`, `-3`… on a clash. It's unique across all kinds and never changes, even when the name does.
- `owner` is a home profile's id (`matt`, `user1`) or `shared`. Deck Lab shows a row only to its owner, and a shared one to both, unless that owner's kit is Public (then read-only to everyone signed in); nobody, the admin included, changes another's. A deck uses only its owner's accessories or shared ones: a deck Played by `user` Matt's, by `wife` User1's, an `either` deck and an intact product shared ones. A deck's Sleeves and Deck box (and its sleeve warnings) show only to whoever owns the deck's accessories; elsewhere another's deck is named only as "one of User1's decks".
- `kind` is `sleeves`, `deck_box` or `playmat`. `name` is required (the product line, such as `Matte` or `Boulder 100+`); `brand`, `colour` and `notes` are optional, one line each. `colour` is the back colour or design, which tells a stray card's possible decks by its back.
- `quantity` (0–9999) **counts individual sleeves** for sleeves, loose ones included, and items for other kinds. Keep a used-up row at 0 for history rather than deleting it.
- `capacity` is how many sleeved cards one deck box holds (1–9999), blank when not known. Only deck boxes have it; it stays blank for sleeves and playmats.
- `image` is blank or `<id>.jpg|png|webp`, a stored picture (the page's photo/link Save or `image put`); every picture must have a row.
- `crop` is blank (show the whole picture) or `x,y,w,h`, the part of the picture to show: left edge, top edge, width and height as fractions of the picture (0–1, at most 4 decimals). Only a row with a picture has one. The picture itself is never cropped. A new or removed picture clears it, except that `image put` under the picture's existing name keeps it.
- `link` is the product page the user pasted, `image_source` the address the picture was downloaded from. No price columns.
- **Write ids in deck headers and an intact product's sleeves and deck box**, never names. A value that isn't an id is treated as older free text: shown as written, never matched by name, and not checked against quantities.
- Rules (Deck Lab warns rather than blocks, except where noted):
  - A row a deck or product uses can't be removed, change kind, or go to an owner that deck can't use (Deck Lab refuses).
  - A deck or product uses only its owner's or shared accessories (Deck Lab refuses other choices).
  - A sleeves design may be used by several holders (built decks and owned products kept intact), and holders may share a sleeve colour; neither is a problem in `accessories check` or on the deck page (whose Sleeves tile just names the others). Choosing a design another holder already uses warns first (Matt, 2026-10-19): the picker, the editor and the Packing plan's Finish building sheet ask first (the picker also offers to move it from a holder you can see), and `deck push`, `deck new` and `product set-kit` save it and print a warning naming the other holders. The Packing plan notes two chosen decks in the same sleeves.
  - A deck box can be shared by as many holders as its `quantity`.
  - A holder whose built list (every section, as for sleeves) has more cards than its deck box's `capacity` is a warning.
  - A holder needs one sleeve for every card of its built list: Commander, Companion, Deck and Sideboard, basic lands included. An intact product needs the total of all its decks. A row with fewer sleeves than that is a warning. Each holder of a shared row is checked against its quantity on its own, not their sum.
  - Sleeves and Deck box lines belong only on built decks, and a product's sleeves and deck box only on owned intact products.

## Accuracy rules

**Never rely on memory** for any of the following. Look them up every time:

- **Card text and rulings:** Scryfall.
- **Commander legality:** Scryfall's `legalities.commander` and `color_identity` fields, plus the current Commander Brackets and Game Changers list. None of this matters for casual 60-card decks.
- **Prices:** show everything in **AUD**, along with the date the price was pulled.
  - Scryfall only gives USD and EUR. Convert with a current exchange rate, state the rate you used, and label the result as an estimate.
  - For purchases that matter, check real prices at Australian retailers, e.g. MTGMate.
- **Commander deck ideas:** EDHREC, for what's commonly played with a given commander.

Card names in any file or deck must match Scryfall exactly. A misspelled name silently breaks the diff between a deck and the collection (and an unknown name in a deck stops its space's table refreshes).

## Data sources

- **Scryfall API** (`https://api.scryfall.com`)
  - Requests need a `User-Agent` header and `Accept: application/json`.
  - Stay under about 10 requests/second.
  - For collection-scale work, use `POST /cards/collection` (up to 75 identifiers per call) or the `/bulk-data` files instead of looking up cards one at a time.
  - Useful endpoints: `/cards/named?exact=`, `/cards/search?q=` (supports Scryfall query syntax, e.g. `id<=wubrg`), `/cards/{set}/{number}`.
- **EDHREC:** Commander staples, synergies, and average decklists.
- **Australian card prices:** MTGMate, and the local shop.
- **pokemontcg.io API** (`https://api.pokemontcg.io/v2/cards?q=...`): Pokémon card data and prices. Prices are in USD or EUR, so convert them.

## Workflows

### Building or refining a deck

1. Confirm whether it's a casual 60-card deck or a Commander deck, and who will play it.
2. Start from what the user already owns. The pool is the Foundations products plus anything bought since. Treat buying cards as a way to fill gaps, not as the starting point.
3. **Account for the shared pool:** a physical card can only be in one deck at a time. When working out owned vs needed, subtract copies already used in other `built` decks and in products kept intact. Flag any conflicts and whether swapping cards between decks is practical. `python -m decklab.lib.pool casual/<deck-slug>` (add `--owned` for the owned-only list) works this out from the inventory and the decks. It needs the local card data, so run `python -m decklab.lib.cards update` first on a fresh clone.
4. Write the deck in Deck Lab (see "Decks"): its text in the scratchpad in the deck text format, with an empty owned-vs-needed table, then `python -m decklab.db deck new <kind> <slug> --from <file> [--space S] -m "..."` and `deck tables <deck-id> --reprice --apply -m "..."` to fill the table with AUD prices. To refine an existing deck, `deck pull` it, edit the copy and `deck push` it with `--expect`, then `deck tables <deck-id> --reprice --apply` when its list changed (and, for a built deck's list, status or Built version, `deck tables --apply` with no ID for the other decks).
5. Check its tokens with `python -m decklab.lib.tokens <casual|commander>/<deck-slug>` (add `--owned` for the owned-only list), or in the Tokens part of the deck page's Cards tab. Missing or different tokens aren't deck problems (a stand-in is fine at home), and don't go on the watchlist unless the user asks, but do offer them as add-ons whenever cards are being bought (see "Researching what to buy").

### Researching what to buy

- Rank purchases by **how much they improve the deck per dollar**. Also favor cards that show up in several decks, especially cards that will carry over into Commander later.
- **Flag reprint risk:** if a card is being reprinted in an upcoming set, say so, because buying now may cost more than waiting.
- Save research to `magic/buylists/<date>-<topic>.md`, starting with the standard historical-research banner:
  `> **Historical research (<date>).** Prices, stock and recommendations below are a dated record, not the current purchase queue. Use [Shopping in Deck Lab](http://localhost:8642/#/shopping) for current needs, the purchase queue and deliveries.`
  Preserve dated prices, stock and rationale; use a newer research file for a new recommendation. These files are not the live delivery or purchase-status source. Link a deck by its Deck Lab page (`http://localhost:8642/#/deck?id=casual/gruul-ramp`), never a deck file. Older banners also link `../watchlist.csv` and `../orders/records/`, and older files link `../decks/...md`: leave them, as those resolve in the `pre-db-inventory` and `pre-db-decks` tags.
- Put intended purchases in the watchlist (`watchlist set --add`, see "The watchlist") with a state and source. When checking shops, check queued cards too and update the dated price/stock fields (`watchlist apply`). A personal wishlist remains a list of interests, and may contain already-owned or incoming cards; it's in Deck Lab's database (see "Wishlists and other database data").
- **Share postage:** buying singles often means several shops, each with its own shipping. Before recommending an order from a shop, check that shop for every other watchlist row (`long_term` included) and suggest the in-stock ones as add-ons, noting any free-postage threshold they'd help reach. Prefer fewer shops over the cheapest price per card when the postage saved outweighs the difference.
- **Tokens in every buylist:** before recommending shop baskets, run `python -m decklab.lib.tokens <deck-id>` for the decks the order is for and the other built decks, and offer the missing or different token and reminder cards that the chosen shops have in stock as add-ons in the same baskets (exact Scryfall face name and token set code). Buying them with a big order saves the separate postage later (Matt, 2026-10-20: a five-shop order went out with no tokens suggested, though the decks needed many). Present them as suggestions, not requirements.
- When the user orders singles or products, record the order (see "Placing an order"), which reduces the fulfilled queue quantities in the same change. Arrival is a separate receipt; do not add incoming cards to inventory early.

### Placing an order

When the user says they've ordered singles or a product, record it in one change:

1. Write its contents in the scratchpad (never `magic/`): the playable cards as a CSV in the collection's columns, any token/reminder singles as a CSV in the token cards' columns, and a sealed product's card list (see "Products").
2. Preview, then record it:
   ```
   python -m decklab.db order add --id 2026-10-12-mtgmate --seller MTGMate --ordered-on 2026-10-12 \
       --source magic/buylists/2026-10-11-otters-upgrades.md --notes "Shop order 12345." \
       --cards <scratchpad>/cards.csv [--tokens <scratchpad>/tokens.csv] \
       [--check "cards=Confirm the Sol Ring is near mint"] \
       [--product fdc-wretched-ranks --product-csv <scratchpad>/list.csv --name "Wretched Ranks" \
        --format "Commander precon (100 cards)" --product-status preordered] \
       --fulfils "Clifftop Retreat@The Free Peoples=2" --fulfils "#12" \
       -m "Record the MTGMate order for Izzet Otters" --dry-run
   ```
   then run it again without `--dry-run`. `--record RECORD.json` can give the record's fields in the records' JSON format instead (the flags fill in or replace them). Each `--fulfils` names a watchlist row as `watchlist list` shows it, with the copies the order covers (all of them without `=QTY`).
3. It checks every name and printing against the card index (`--no-check` skips only the printing and finish checks), saves the record, its components, the product, the watchlist reductions and the refreshed deck tables as one change. It refuses a change after which the deck tables couldn't be refreshed, such as a payload whose every card is already in the collection (`--force` saves it anyway, without the tables' refresh). That also matches a real order for more copies of printings already owned, not only a duplicate entered by mistake: for one of those, give `--extra-copies cards` (the component's id: a product's is its stem; repeatable) instead, which marks it as extra copies of owned printings so the pool doesn't warn about it (an order already recorded is marked with `order extra-copies`, below). Ask the user first that the copies really are extra, not cards already added to the collection by hand. Once an unmarked order like that is forced, every other order's receipt and every deck-table refresh is refused (the pool is incomplete) until it arrives or is marked, so warn the user before forcing.
4. If the order came from a buylist, add a dated "Order update" line under its banner naming the order id, and commit it.

Fixing a pending order (each with `-m`, and `--dry-run` to preview):

- `order edit ID C --csv FILE` replaces a pending cards or tokens component's rows (the same total quantity and, for cards, the same copies of each name; printings checked). Get the current rows with `order show ID --csv C`.
- `order record ID [--seller S] [--ordered-on D] [--notes T] [--source PATH ... | --clear-sources]` corrects only the supplied record fields at any receipt status, preserving its id, components and audit notes. Repeated sources replace the whole list; an empty string clears a text field. The order date cannot follow an existing receipt. No card data or table refresh is needed. Shopping's **Edit order…** offers these fields and, for pending parts, adding or withdrawing an arrival check, with a preview before each audited save.
- `order checks ID C --add TEXT` adds a check for arrival; `--withdraw N` drops one added by mistake. Checks on a pending component can't be resolved before it arrives: the receipt verifies them.
- `order split ID C --new-id NEW --take ROW[:QTY] ...` moves rows (numbered as `order show` numbers them) into a new pending component, for a partial shipment; each check goes to both parts unless `--move-check N` (only the new one) or `--keep-check N` (only the original).
- `order cancel ID C [--restore-queue] -m "..." --reason "..."` cancels a pending cards, tokens or product component, retaining its history and reason. Add `--restore-queue` to return its recorded fulfilled queue quantities; the command-line default is not to restore. Shopping's **Edit order > Cancel part** asks for the reason and offers restoration with an explicit checkbox, checked initially. The preview shows the exact queue quantities and affected deck tables before one audited save. After cancellation, the command lists buylists linked to a cards or tokens payload for manual follow-up.
- `order remove ID -m "..." --reason "..."` removes an order entered by mistake, including its components, payloads and products, and always returns its recorded fulfilled queue quantities. Any received component refuses the whole removal. Shopping offers the same previewed change under **Edit order > Remove order**.
- New orders keep price-free fulfilment intent and physical allocations in a reserved `audit_notes` ledger; do not edit its marker by hand. Splits conserve those allocations. Product-list corrections retain the original fulfilled intent and quantity even if the list shrinks, with a warning. Token-name corrections preserve the original intent and remap it to remaining physical capacity, with a warning; later splits conserve it. Card corrections keep each name's total. Restoration offers the original recorded purchase request, which may differ from the corrected contents; it never invents replacement intent. Each cancellation consumes its offer even when restoration is declined, preventing a later removal from restoring it twice. Existing queue metadata is retained when copies return; newly recreated rows have blank market-reference fields. Older orders without the ledger require manual queue review: no quantities are inferred from their contents. Both the queue changes and deck-table refresh save with cancellation or removal. Shopping keeps the saved result and any **Tables out of date** link visible until Done.
- `order merge ID OTHER... [--rename OTHER:COMPONENT=NEW] [--notes T] -m "..."` combines orders one shop sent as one parcel (combined postage), so the delivery is received once: every component of each OTHER moves into ID with its rows, checks, status and recorded fulfilment, and the OTHER records go. A component id ID already has needs `--rename` (such as a second `cards` as `additions`). The orders must share a seller and have nothing received; sources are combined and notes joined unless `--notes`. Payloads keep their files, so the deck tables' labels don't change.
- `order extra-copies ID C -m "..."` marks a pending cards or product component as extra copies of printings already owned, when the pool warns that "every card in" it "is already in the collection" but the order really is for more copies (`--undo` takes the mark off). The mark is one sentence in the record's `audit_notes` (`Extra copies of owned printings: cards.`); never write it by hand. It refreshes the deck tables like the other order writes, and is refused for a received, cancelled or tokens component. A part split off a marked component isn't marked, so mark it too.

### Wishlists and other database data

Wishlists, profile settings, the simulations mode and play records live in Deck Lab's PostgreSQL database, not in files: never recreate `magic/wishlists/`. Read and change a wishlist only with these commands (system `python` from the repo root):

- `python -m decklab.db wishlist list <profile>` prints it in list order (`--json` for the old file format).
- `python -m decklab.db wishlist add <profile> "<name>" [--set S --number N] [--notes T] [--source PATH] -m "<what and why>"` adds a card at the end. The name is checked against the card index and stored as its exact Scryfall name; `--no-check` skips only that lookup (when the index isn't built). `add` never changes a card already on the list (it exits 0 and says so): use `set`.
- `python -m decklab.db wishlist set <profile> "<name>" [--notes T] [--source PATH] [--set S --number N | --no-printing] [--no-check] -m "..."` changes a listed card's notes, source or printing.
- `python -m decklab.db wishlist remove <profile> "<name>" -m "..." --reason "<why>"`.
- Every write needs a non-blank `-m`, and a removal a non-blank `--reason`; each becomes one change set by Claude by default in the audit trail. A profile not in `decklab/config.json` is refused unless `--allow-orphan` is given. Exit codes: 0 done, 1 refused or nothing to do, 2 the database can't be reached.
- On Deck Lab's Wishlist page a card's sheet changes its notes, printing and source too (the same `set` change), and Remove has an Undo that adds it back with them, at its old place in the list.
- **Privacy:** a wishlist is private to its owner. On Deck Lab's page only its owner sees it, notes included: `GET /api/profiles/<id>/wishlist` answers 403 to anyone else, an admin included, and to a home page that hasn't named a profile; on the Activity page its rows show only to its owner, and a change's `-m` message and `--reason` only to a viewer who sees every row of it and may see the words (so a default Claude command's message about Matt's list reaches only Matt; about another person's list it reaches nobody, unless --actor names that owner). On the PC, everything (lists, notes, messages and reasons) can still be read through `wishlist list` and `sql`.

To read anything else in the database, use `python -m decklab.db sql "select ..."` (`--csv` for CSV). It runs as a read-only role, so it can't change anything. The phase 2 tables are `wishlist_entry`, `profile_setting`, `simulation_mode`, `play_record`, and the audit trail `audit.change_set` / `audit.row_change`; the inventory's are listed under "The inventory", the decks' under "Decks" and the accessories' under "Accessories"; the others are `space`, `profile`, `profile_email`, `ops.backup_run` (each backup, export, restore check, gate run and nightly `check`) and the visits, `ops.visit_day` and `ops.visit_page` (who visited Deck Lab each day, from home or outside, and the pages they opened; not audited or exported, kept about a year; `python -m decklab.db visits` summarises them). Change settings, the simulations mode and play records on Deck Lab's page, not in SQL.

### Logging new cards

- **A recorded delivery:** preview `python -m decklab.db receive --order <id>`; apply only the components the user says have arrived, with `--component <id>` (repeat it; omitting it selects every pending component), the actual arrival date and `--apply`, such as `python -m decklab.db receive --order <id> --component cards --verified cards --date YYYY-MM-DD --apply`. For part of one component, split it first (see "Placing an order").
- **Physical checks:** a cards component with checks, and every tokens component, needs `--verified <component>`, which says its checks were done and its rows hold the actual received facts. Record what the checks found first: `order show ID --csv C > <scratchpad>/c.csv`, correct the copy (conditions, languages, printings, finishes, a token's real back), `order edit ID C --csv <scratchpad>/c.csv -m "..."`, then receive with `--verified C`; or give the corrected rows at the receipt with `--rows C=FILE`. Either way the total quantity (and, for cards, the copies of each name) must stay the same. Unknown condition and language stay blank. Token rows must keep their physical front/back pairing, have no unresolved pairing note, and say `single-sided verified` for a genuinely blank reverse.
- **A product** needs `--intact yes` (kept as its decks, in its own sleeves and box) or `--intact no` (broken up into the shared pool), not `--verified`. Its token checks stay open: once its physical tokens are inspected, add them with `tokens add`, then resolve the checks with `order checks ID C --resolve N` (or `--clear`), which keeps them as `verified_checks`; on Deck Lab, an admin marks one done with **Done** under Shopping's Follow-ups (the same resolve, with Undo for a few seconds).
- The receipt adds the cards to the collection (plain basics left out) or the tokens to the token cards, marks the components received, sets a product `owned` with its intact choice (`no` also clears its sleeves and deck box), and refreshes the deck tables, all in one change. It refuses components already received or cancelled. On Deck Lab's Receive delivery page (`#/receipt?order=<id>`, from a delivery on Shopping) it applies only if the inventory hasn't changed since its preview: any save in between (a Tokens or Collection page save included) makes it ask for a new preview. That check is the page's only: on the command line a preview run and a later `--apply` run aren't linked, and each `--apply` re-checks its blockers against the inventory at that moment, so re-run the preview if anything may have changed. Exit codes as above: 1 refused or something still required, 3 received but the tables couldn't be refreshed.
- **Cards from no recorded order** (a scan, a trade, a gift): `collection merge` (see "Collection cards"). It isn't a route around a receipt's checks.
- Confirm the result by reporting how many rows and cards were added. If the cards came from a sealed product that's already recorded, say which product.
- After changing orders or the purchase queue, run `python -m decklab.lib.purchases --check` to validate record coverage, receipt states and queue fields.

## Conventions

- Scripts are Python 3 (3.14 is installed). Use only the standard library (`csv`, `json`, `urllib`) unless a dependency clearly earns its place. The one exception so far is psycopg (`decklab/requirements.txt`), installed in the repo's `.venv`. Use the system `python` anyway: the server, the tests, `python -m decklab.db` and the command lines that read the inventory and decks (`pool`, `purchases`, `tokens`, `accessories`, `forge`, `goldfish`, `stats`) put the `.venv`'s packages on `sys.path` themselves (`decklab/lib/venv.py`), and the background server's task stays on the system `pythonw.exe` (the `.venv`'s python.exe is a launcher that starts a second process). Without a usable `.venv` everything still imports: the database counts as unreachable (pages say so, writes to it answer 503, and the inventory's command lines exit 2) and the database tests skip. A git worktree has no `.venv`, so run database tests there with the main repo's `.venv\Scripts\python`.
- **Commit before restarting Deck Lab.** After changing Deck Lab's code, validate and commit the completed changes first, then restart the background server if it's running (`python -m decklab.lib.homenet restart`), since it keeps running the old code. The server records whether application files were uncommitted at startup, and that warning persists even after a later commit. Before handing the task back, check `/api/status` and confirm `build.running_dirty` and `build.latest_dirty` are false and `build.restart_required` is false. If a test restart captured uncommitted changes, restart again after committing so the user isn't left with the warning. If it isn't running, leave it stopped: the user starts it by hand (`restart` would start it). A server started for testing needs another port and `--host 127.0.0.1` (for example `--host 127.0.0.1 --port 8643`): the background server holds 8642, and a server on every network interface, on a port no firewall rule covers, makes Windows ask about Python's firewall access. A test server uses the live database, like the background server, so anything saved through it, the inventory and decks included, is real.
- The inventory, the decks and the accessories are never files: change them only through `python -m decklab.db` or Deck Lab's pages, never by recreating their CSVs, deck `.md` files or pictures in `magic/`, pushing back an export, or writing SQL. A pulled or exported deck is a copy in the scratchpad: change the deck with `deck push`. There's no way back to the files: phase 5b (2026-10-14) retired the rollback tooling (its last commit is the tag `pre-phase5b`); a lost database comes back from a backup (decklab/README.md, "Database").
- Keep CSVs still kept in git (the Pokémon files) and those you hand to a command sorted by `set`, then `collector_number`, so diffs stay readable. The inventory keeps its own rows sorted.
- Don't remove cards from a collection when they're sold or traded without asking first. A removal (on the Collection page) can carry a reason (optional); ask the user to enter why when cards are sold or traded.
- **CI** (GitHub Actions, `.github/workflows/`): `tests.yml` runs the whole unittest suite on pull requests and pushes to main that change code, config, test inputs or other non-documentation paths, and always weekly (Sunday 03:00 at home) and by hand, split across 4 parallel jobs on Windows and 4 on Linux by `scripts/test_shard.py` (test modules dealt round-robin in name order, about 5 minutes each), and its `linux-services` job installs, restarts, crashes, stops and removes the nightly timer and the server's service under a real systemd user manager (`scripts/linux_services_check.sh`, E11-S33). The cheap `changes` job uses `scripts/ci_changes.py` to skip the shards and `linux-services` for known documentation-only changes (Markdown/reStructuredText in the documentation locations and the design diagram); Markdown deck fixtures still need tests. Unknown or unavailable comparisons run the suite. Its `tests` job passes when every shard and `linux-services` did, or when successful documentation-only detection skipped them: that's the one check to require before merging. A shard still running after 10 minutes prints every thread's stack and exits, so a hang shows where it is. The runner has no PostgreSQL, `.venv`, card data or Forge, so the database tests and real-Forge games skip there, and it may have an 8.3 temp path (`RUNNER~1`), fewer cores than Forge workers and a below-normal process priority: a new test must pass (or skip) on it, not just on the PC. `lint.yml` runs ruff on every push and pull request, documentation-only changes included, for real errors only (`E9,F63,F7,F82`: syntax errors, undefined names), not the full style rule set. To run one shard locally: `python scripts/test_shard.py INDEX COUNT [--hang-after SECONDS]` (INDEX from 0). A new test must pass on Linux too: no Windows paths, case-insensitive names or Windows-only calls without a skip or a platform patch.
- **Commit as soon as a task is done.** When a task changes files (buylists, reports, code, docs), commit at the end of that task. Don't push unless asked. Never leave changes uncommitted while waiting for something to happen. Inventory, deck and accessory changes aren't commits: each command saves its own change set (an inventory change with the deck tables it refreshes).
  - Placing an order is one `order add` (record, payloads, product and watchlist reductions together), plus a commit of any buylist notes.
  - Its arrival is one `receive --apply`.
